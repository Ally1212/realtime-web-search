## 这次怎么测的

**发起查询 → 中台派单 → 采集器采集 → 提交中台 → 等待保存完成 → 从中台读回固定版本 → 核对并导出。**

1. 用 Consumer Key 发起 `POST /v1/live-queries`，保存查询ID和任务ID；对应 Collector Key 注册并领取任务。
2. 采集真实结果，调用 `POST /v1/documents/bulk`，请求头带 `X-Ingest-Class: realtime`。轮询 `/v1/ingest/receipts`，等到 `accepted/duplicate`，取得文档ID和版本ID后完成任务。
3. **根据这组文档ID、固定版本ID，从中台重新读取完整数据**，不是直接拿本地采集结果展示。逐字段比较并校验SHA256，再生成CSV/JSONL，重新读取文件深比较。

这是按请求触发的异步流程，**“实时”不等于提交后立即可读**。`queued`只是受理，`retrying`表示还在重试；即使已有`accepted`，也要实际读回核对后才算通过。

## 同事测不通，先检查这几项

- **环境与权限**：确认代码版本、请求入口、Dataset和平台范围一致。Collector Key负责采集写入，Consumer Key负责查询读取；创建Key不等于完成授权，组织策略和应用授权都要允许`live_query`，并具备快照、原始载荷等读取权限。Web/News/Trends用`social_media_raw`，Maps用`google_maps_raw`。
- **异步状态与限流**：保留原幂等键，按回执状态继续等待；429按退避重试。不要换键反复建任务，也不要把queued当入库成功。Maps位置用`conditions`，不要用已被忽略的`source_options`。
- **读取接口与hash**：本次遇到逐文档快照接口只返回指标行，而官方`POST /v1/snapshots/payloads/batch-get`可返回完整载荷。补读必须绑定原document_id、snapshot_id、snapshot_at和固定版本的raw_payload_hash；不能拿“最新版本”代替。真实计数等`platform_metrics`要在提交前确定并参与载荷hash，避免中台补字段后摘要不同。

仍不通时，请提供：**环境/代码版本、来源和参数、HTTP状态及错误码、query/task/document/version ID、回执状态与时间**。不要发送密码、Key或Authorization请求头。这样才能定位卡在授权、采集、保存还是读取。
