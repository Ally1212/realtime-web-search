# 每日 10 万条采集：开源方案与项目瓶颈调研

调研日期：2026-09-15。依据：当前源码、运行中统计服务的只读快照、实验数据库只读聚合、开源项目官方文档，以及 Stack Overflow / Hacker News / GitHub 讨论。

**建议保留 Scrapy + Trafilatura，优先改造日量实验的执行流水线、减少重复处理、提高真实发布时间覆盖率，再验证 Google 的持续新链接供给。当前证据不支持通过换框架或只加并发实现每天 10 万条 Whale 入库。**

本文暂按“每天新增、相关、正文有效、历史去重、取得 Whale 接收回执”验收，保留当前 Google 发现约束。Sitemap / RSS / API 是允许扩展来源时的候选路线，尚未实施。每天采集历史文章，与每天取得当天发布的新文章，是两个不同目标；后者还受实际内容供给约束。

## 1. 实际瓶颈：先看本项目

最新正式实验为 `daily-zh-whale-20260914-v4`，仅中文。快照采集时间为 2026-09-15 09:56（UTC+8）。实验处于 **paused**，容器仍运行、心跳新鲜；最近一分钟产量为零，不能解释为正在满负荷抓取却没有产出。本次未恢复或重启任务。

| 指标 | 观察值 | 含义 |
| --- | ---: | --- |
| 累计在线时间，含搜索冷却、不含暂停 | 约 16.08 小时 | 未完成连续 24 小时验收 |
| 实际 Google 通道调用 | 14,032 | 不等于调度记录数 |
| 成功通道调用 | 13,696，约 97.6% | 请求成功不代表得到新正文 |
| 搜索返回链接条目，含重复 | 130,028 | 不能算采集成果 |
| 唯一发现 URL | 29,979 | 跨页、跨查询大量重复 |
| 正文处理记录 | 62,606，涉及 29,978 个 URL | 32,628 次属于同 URL 的后续处理，约占 52.1% |
| 有效新正文 | 15,838 | 当前自动质量与精确哈希口径 |
| Whale 接收 | 3,735 | 仅有效新正文的 23.6% |
| 缺少发布时间、未投递 | 12,103 | 占有效新正文的 76.4% |
| 待投递 Outbox | 0 | 该快照的主要入库损失不是上传队列积压 |

只读 API 原始指标保存在 [快照](research/crawl-capacity-2026-09-15-snapshot.json)。上述搜索条目、正文重复次数、错误分类来自同一暂停实验的数据库聚合；次数是处理记录数，不是互不重复网页数。

主要损失如下：

| 位置 | 已验证事实 | 优化方向 |
| --- | --- | --- |
| 发布时间 | 12,103 条有效正文被 `blocked_missing_publication` 阻挡；解析只接受有限的 HTML / JSON-LD 字段及明确时区 | 增加站点日期适配与可信字段解析；不能用抓取时间冒充发布时间 |
| 重抓与无效处理 | 34,762 次处理无效；其中 robots 拒绝 13,983 次、正文不足 100 字符 4,154 次、HTTP 403 为 2,305 次、PDF 不支持 1,670 次 | robots / 内容类型负缓存；按失败原因分配复查周期；新 URL 优先，更新队列独立 |
| 搜索调度 | 10,693 条搜索失败记录中，10,587 条是 `google_proxy_unavailable` | 按最早可用时间重新调度，避免短周期重复探测；单独统计调度失败与实际 HTTP 失败 |
| 正文执行 | 每条 URL 都调用 `subprocess.run()`，重新创建 `DatedFetcher` | 常驻 HTTP 执行器；复用连接及 robots 缓存；保留卡死任务的硬截止 |
| 主循环 | 同步 `self.search(row)` 和 `flush_whale()` 与正文结果回收、补充任务共用主循环 | 搜索、正文、上传分别运行，以有界队列连接 |
| 上传容量 | 每次最多 25 条，下一次最早 20 秒后开始 | 理想上限仅 108,000 条/天，几乎无重试余量；达到更高供给后应增加批次及独立上传能力 |

进一步说明：

- `LiveFetcher._request()` 每次创建新的 `requests.Session()`；缓存又随单篇子进程退出而消失，跨网页无法复用。连接建立、robots 请求和 Python 模块导入都存在可消除开销，但本次没有做 CPU profiling，不能给出确定提速倍数。
- 单域 semaphore 在任务进入线程池后才获取。如果已提交任务集中在一个域名，部分线程会等待该域名，其他域名不能及时补入。这是代码可见的调度风险，尚未测量它占实际耗时的比例。
- `due_urls()` 已按 `last_fetch` 优先未抓 URL，但同 URL 再次被发现后仍会触发复查：有正文通常 6 小时，没有正文通常 1 小时。应区分永久不适用、可恢复错误和有价值更新，不能一律短周期重试。
- 数据库使用 SQLite WAL + `synchronous=FULL`，正文提交逐条进行。保留耐久性，通过事务批量写入和单写入者减少提交开销；不应先关闭同步保护。当前没有测量磁盘瓶颈。

源码依据：[实验执行器](../realtime/google_experiment.py)、[HTTP 抓取与抽取](../realtime/fetcher.py)、[重抓与分类](../realtime/experiment_store.py)。README、旧实验文档仍有“4 并发”字样，当前源码的 `BODY_WORKERS` 为 **12**。

另一个入口 `continuous-whale` 使用常驻 Scrapy，但 `persistent_executor.py` 将全局并发按最大爬虫数分配；默认 `32 // 12 = 2` 个请求/爬虫，8 个活跃爬虫约有 16 个请求槽，12 个约 24 个。这与上述独立实验不同，不能认为调整 `CRAWLER_CONCURRENCY` 就会改变实验的 12 个正文 worker。

## 2. 每日 10 万条需要什么能力

`100,000 / 86,400 = 1.157` 条/秒，即每小时约 **4,167 条最终新增成果**。若每天实际可工作 20 小时，则工作期间需约 **1.389 条/秒**。

完整产量取决于搜索发现、正文抓取、抽取与去重、发布时间覆盖、上传成功各环节。容量取最慢环节，不能把搜索 RPS 或 HTTP 200 数当正文产量。

用当前快照作诊断性估算：

| 当前样本比率 | 数值 |
| --- | ---: |
| 每次实际搜索调用对应有效新正文 | 15,838 / 14,032 ≈ 1.129 |
| 每次实际搜索调用对应 Whale 接收 | 3,735 / 14,032 ≈ 0.266 |
| 保持当前转化率，实现 10 万 Whale 接收所需搜索量 | 约 375,700 次/天，即 4.35 RPS |
| 假设有效正文均有可接受日期且上传成功，所需搜索量 | 约 88,600 次/天，即 1.03 RPS |

这是假设比率不变的计算，**不是提速后的预测**。扩大范围后，重复率、目标站点、代理可用率和相关性都会变化。现有搜索上限 2 RPS 下，若保持当前 0.266 条/请求，仅按搜索供给计算也只有约 46,000 条/天；实际主循环还有其他限制。

当前约 16.08 在线小时的平均速度折算为约 23,600 条有效正文/天、5,600 条 Whale 接收/天，只用于比较差距，不是已完成日量。该折算还排除了暂停；正式验收必须按完整自然流逝时间计算。

正文侧的示例容量规划：假设抓取到最终有效新正文的比例为 50%，日期/投递通过率为 80%，需要约 250,000 次正文抓取/天，即 2.89 次/秒。若平均处理时间 5 秒，理想并发约 15；可从 **32 个全局 HTTP 槽、单域 1–2 个槽**开始阶梯测试，再根据队列与资源决定是否升至 64。这里的比例和延迟是规划假设，不是现有实测。

## 3. 开源方案对照

本次核验了以下项目的官方说明，没有部署这些候选并跑同一数据集基准。宣传中的“每秒千页”“覆盖百分比”不用于本项目容量承诺。

| 方案 | 主要能力与适用位置 | 对当前项目的判断 |
| --- | --- | --- |
| **Scrapy + Trafilatura** [1][8] | HTTP 并发、域名调度、重试、正文提取；已有集成 | **首选**。改造实验执行器，复用现有抽取、质量、Outbox；保留日期与实验隔离口径 |
| **aiohttp + Trafilatura** [4][8] | 常驻异步 Session、连接池，适合专门的正文 worker | 可作为较小的替换后端；调度、重试、持久化需复用现有系统或自行实现 |
| **Crawlee** [2] | HTTP / Cheerio 与 Playwright 等执行器；按内存/CPU 自动伸缩 | 值得借鉴资源反馈与浏览器分层；整体迁移 JS 栈收益未证明 |
| **Crawl4AI** [3] | 多 URL 并发、内存自适应调度、流式结果、结构化提取 | 适合需要浏览器的页面及提取实验；不能解决 Google 新 URL 不足，不建议所有页面都走浏览器 |
| **Scrapling** [10] | HTTP/浏览器会话、并发 Spider、暂停恢复、自适应选择器 | 可对易变页面作小样本比较；重点评估有效正文率和内存，不把其反爬宣传当实测结果 |
| **Colly** [5] | Go 的异步抓取、域名并发、缓存与会话 | 如果未来确认 Python 执行开销成为主瓶颈，可做 HTTP worker 对照；目前重写成本高于已知收益 |
| **scrapy-redis** [6] | 多个 Scrapy 实例共享请求队列、去重与后处理队列 | 多机时再考虑；项目已有 Valkey / PostgreSQL，要避免维护两套不一致的任务状态 |
| **Apache Nutch** [7] | 基于 Hadoop 数据结构的批量抓取与插件体系 | 适合更大规模索引和历史批处理；当前 10 万条/天不构成迁移到 Hadoop 的充分理由 |
| **Apache StormCrawler** [9] | 基于 Apache Storm 的低延迟、可扩展爬取 | 适合已有 Java / Storm 运维体系；本项目引入成本较高 |
| **Firecrawl 自部署** [11] | 通用 scrape/crawl/map/search 服务与 Markdown 输出 | 适合需要统一 API 的场景。自部署不等同云服务能力，额外抓取引擎不随默认部署提供；需评估服务组件成本及 AGPL-3.0 许可 |

SearXNG、curl_cffi 和 Playwright 已在项目中。SearXNG 在当前 Google-only 设置下仍依赖 Google 上游，不会创造独立的 URL 供给；全量切换浏览器也不能消除重复和缺失日期。

## 4. 社区经验：哪些值得采用

### Stack Overflow：23,770 页耗时 28 小时的案例

[Speed up web scraper](https://stackoverflow.com/questions/17029752/speed-up-web-scraper) 的采纳回答建议检查自定义中间件、并发、CPU/内存、DNS 和目标站限速，逐条 yield 结果；另一回答建议缓存以避免重复请求。本次通过 Stack Exchange API 读取原问题及答案。

对本项目有用的是 **测量等待在哪里、缓存可复用结果、持续输出而非批量等待**。帖子较旧，其中 PyPy、旧 Scrapy API 等建议需另行验证；不照搬关闭所有日志的做法，保留产量与故障证据。

### GitHub：并发调得越大，速度可能越低

[Scrapy #5182](https://github.com/scrapy/scrapy/issues/5182) 的报告者设置极大的 `CONCURRENT_ITEMS`，描述 CPU 100%、从正常约 400+ 页/分钟降至约 40 页/分钟，并给出复现代码。这是特定版本、特定环境的历史案例，不能推断当前版本也有同样问题。

可采用的方法是 **32→64 的阶梯测试，观察最终新增量、CPU、队列年龄与内存**，避免一次把并发改到几百几千。

[Scrapy #6476](https://github.com/scrapy/scrapy/issues/6476) 讨论零下载延迟造成的突发请求；[官方性能文档][1] 同样强调目标站可承受能力。这支持使用域名公平调度和针对 429/503 的退避，而不是让慢域名、错误重试占满全局资源。

### Hacker News：下载、分类、存储要一起规划

[Ask HN: Advanced web crawling resources?](https://news.ycombinator.com/item?id=14223259) 中有参与者强调分类、存储和检索成本，另有人描述通过 Redis / 任务队列拆分抓取。该讨论没有足够可复现数据支持其中的极高吞吐估算；本文只采用流水线拆分的工程思路。

这与本项目同步搜索和上传占用调度循环的情况直接相关：**搜索慢时，已有 URL 的正文下载仍应持续；Whale 慢时，正文结果应先进入可恢复 Outbox。**

Reddit 本次访问受限，搜索引擎入口也出现验证页，因此没有引用未读到正文的 Reddit 帖子。社区证据以实际读取的 Stack Overflow、GitHub、HN 为准。

## 5. 建议实施顺序

### 第一阶段：修复浪费与验收损失

1. **建立可追溯的真实日期提取。** 除现有 JSON-LD / article meta，适配主要贡献站点的页面日期和明确时区规则。来源允许后，可用同文 RSS/API 的明确发布时间补充。Sitemap `lastmod` 是修改时间，不能当发布时间。若原站确无日期，该条仍需单列；是否调整 Whale schema 是另一项产品决定。
2. **按失败类型持久化调度。** robots 按 origin 缓存并定期刷新；PDF/视频在当前未支持时分流；404、确定非文章页采用较长复查周期；429/503 尊重服务端反馈；临时网络失败有退避和重试预算。日期未知内容在现有 remote-only 路径下已清理正文，新解析器不能保证直接恢复全部 12,103 条，需按候选价值安排补抓。
3. **补齐漏斗指标。** 同时展示实际搜索请求、新 URL、首抓/复抓、有效新正文、有日期正文、Whale 接收；按域名和查询计算每单位时间的新成果。`google_proxy_unavailable` 要与已发出的请求失败分开。

### 第二阶段：改造执行流水线

推荐结构：

```text
Google 查询调度 → 新 URL 去重队列 → 常驻 HTTP worker
                                      ↓
                                提取与真实日期解析
                                      ↓
                                质量判断、正文去重
                                      ↓
                                持久 Outbox → Whale

动态网页 → 小规模浏览器队列
需要复查的旧 URL → 独立低优先级更新队列
```

搜索调用独立运行，仍共享已有 Google 全局配额、代理健康和缓存，不靠增加进程倍增配额。正文 worker 复用按站点/会话隔离的连接池及 robots 缓存；域名配额在任务入执行器前获取，避免线程等待单域锁。迁移异步抓取时保留公网地址校验、重定向校验、下载大小限制和任务硬截止。

保留本地实验 SQLite 的单写入者，正文结果按小批次事务写入；队列有容量上限与租约恢复。不要把一个 SQLite 连接直接跨多个线程共用。正文抽取只有在 profiling 证实占 CPU 后，再移至常驻进程池。

上传以**数量或时间任一达到即发送**：候选起点为 50–100 条/批、1–2 秒检查，保留幂等、退避及回执逐条核对。具体批量取 Whale 实际允许值，尚未验证 100 条批次。上传额定能力建议覆盖目标至少两倍，以容纳错误重试和临时积压。

### 第三阶段：解决持续供给

**保持 Google-only 时：** 扩大有产出的独立关键词、实体、站点和时间分片；观察“每请求新增正文”和“每请求最终入库”，避免固定热词反复首页轮询。当前约 500 个启用查询、每个 11 页，并不代表无限新内容；即使假设每页 10 个互不重复 URL，一轮也只有约 55,000 个候选，真实跨查询重复会进一步减少供给。若仍要求固定前 11 页覆盖，可保留覆盖任务，将新增优化放在查询目录与到期频率。

**允许扩展来源时：** 用 Google 找到高产站点，再通过 Sitemap、RSS/Atom、公开 API 和有范围限制的站内链接发现正文。[Scrapy SitemapSpider][12] 和 Trafilatura 的发现组件可复用。逐 URL 保存 `discovery_source`，这些页面不能继续标记为 Google 直接发现。先对几十个候选站点实测“每日新正文、日期覆盖率、重复率”，再扩大目录；Sitemap 适合历史回填，RSS/API 更适合增量，但也不保证每天有足量新文章。

## 6. 验证与停止条件

先用同一批已发现、不同域名的 1,000–3,000 个 URL 对比现执行器和常驻执行器，固定质量与日期规则，分开报告冷缓存与热缓存、抓取成功与最终新增。避免不同时间新链接供给差异掩盖执行器效果。

随后阶梯测试正文并发 12/32/64，记录各阶段 P50/P95、队列占用、域名等待、CPU/内存、失败类型与每秒有效成果。机器可先用现有环境；若需要独立常驻主机，可将 4–8 vCPU、8–16 GiB RAM 作为 HTTP 为主的试验起点，浏览器负载另测，不能据此保证产量。

最后做连续 24 小时验收，再连续运行至少 3 天检查新 URL 是否衰减。按每个完整 24 小时窗口计新增 Whale 接收，不把同文重复、更新、过去的历史量、截止后回执混入。`queued/accepted` 是现有客户端认可的回执；若用户要求 Whale 最终可检索，还需要增加远端最终状态核验。

如果正文队列持续为空，继续加正文 worker 无效，应改善发现供给；如果日期覆盖率仍低，继续加抓取 RPS 无法按同等比例增加入库；如果 CPU 或错误率升高而最终产量不升，应停止增并发并定位原因。

本次完成的是调研和只读核验，未修改采集代码、运行参数或任务状态，未执行新一轮爬取/上传压测。候选方案速度比较、日期可恢复比例以及连续 10 万/天的可达性，均需上述实验验证。
