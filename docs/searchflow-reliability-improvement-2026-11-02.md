# SearchFlow 网站可靠性优化需求与验收

日期：2026-11-02。

## 目标与范围

保持“指定关键词和地区 → 创建任务 → 后台采集 → 保存 → 查看、分析、导出”的业务流程。
本轮不调整关键词供给、采集频率、代理数量或并发；不增加商业化功能。

1. 首页统计不再为了四个数字触发完整深度分析。统计必须真实，说明时间范围、生成时间及投影是否完整。
2. 任务和结果列表明确区分读取中、读取成功和读取失败。请求有等待上限，失败可手动重试；
   保留上次成功内容时必须明确其不是最新读取结果，不把读取失败显示为零数据。
3. 保持筛选、分页与导出语义。Trends API CSV 保留现有七列，补充话题下的报道行；
   话题行和报道行分开，CSV 行数不冒充链接数；JSONL 仍是完整结构出口。
4. 网络超时后不自动重复创建、启动、暂停或上传任务。写请求结果不确定时提示先刷新核对。
5. 不以更换搜索技术或重写架构代替已确认问题的修复，不承诺上游搜索必定成功或固定速度。

## 已确认的基线

- 原始请求 39,835，历史正文记录 332,768；公开分析请求 39,830，投影待同步 0。
- 公开近 90 天窗口去重链接 522,676，查询词 29,601；这些不是当前日新增量。
- 首页复用了 `/api/product/analytics/overview?days=90&source=all`。
  只读分段测量：请求汇总约 0.607 秒，完整内容分析约 15.645 秒；
  原分析 SQL 的单条语句超时为 20 秒，生产日志有 `QueryCanceled`。
- 本轮复查时已有缓存的公网接口约 0.572 秒，首页可恢复显示。
  因此问题是冷计算链路过重及恢复体验不足，不宣称每次打开都失败或已经证明所有超时根因。

## 约束

- 自动采集、正文、Whale 上传/领取、监测保持现有关闭状态。
- 不创建真实搜索或上传任务，不修改历史数据，不运行旧正文/hash 迁移。
- 保留前置访问验证、管理员和客户权限、私有结果隔离。
- 只发布经过比对的最小 Web 变更。生产 `web.py` 存在既有差异，不以本地整文件覆盖；
  不重启采集 worker、OpenSERP、代理、数据库或其他站点。
- 发布前备份，发布后检查数据、开关、服务及页面；失败回滚本轮变更。

## 验收标准

- 轻量汇总与同范围独立数据库复算一致，包括空数据、来源筛选、UTC 边界、私有隔离及投影延迟。
- 首页汇总失败不会影响最近结果；有重试和明确的旧数据/部分数据标识。
- 列表超时、非 JSON 错误、快速切换筛选后能恢复，不残留永久加载状态，不把旧响应覆盖新条件。
- Trends CSV 报道链接逐项与 JSONL 原始结构核对；Web/News 七列表头与既有行为保持。
- 使用独立测试数据库/队列回归；线上仅验证已有数据与下载，不开启采集。
- 桌面和手机浏览器验收；测试数、耗时均写实际值，不把一次测量称为 SLA。

## 更准确的提问模板

> 请优化现有 SearchFlow 线上网站的可靠性，不改变我指定的关键词、地区、采集规则和原有功能。
> 优先修复首页统计读取异常，让任务和结果列表有明确的加载、失败、超时与重试状态，
> 并保证页面筛选与导出的数据范围一致、Trends 导出不遗漏相关报道。
> 请先定位问题并整理验收标准，再做最小代码修改、隔离环境测试、备份和部署，最后验证线上效果。
> 不开启自动采集、正文、平台同步或监测，不运行历史迁移，不覆盖生产既有差异。
> 完成后只报告改了什么、真实验证结果、尚存限制和回滚位置。

## 实施与验收结果

已上线。发布范围仅 `analytics.py`、`product_http.py`、`workbench_ui.py`、`reliability_ui.py`；
生产 `web.py`、`serp_page.py` 哈希保持不变，只重启 `google-workbench-web-1`，未重启采集机五个容器。
服务器回滚备份：`google-workbench/state/reliability-20261102/backup/`。

- 首页改用轻量 `/api/product/analytics/summary`，只计算请求、查询词、窗口去重链接和最后保存时间；
  保留私有数据隔离、UTC 边界、投影状态、生成时间和最多 60 秒缓存。
- 任务/结果/首页汇总增加读取中、成功、失败、旧数据标识和手动重试。读取 20 秒上限；完整分析 30 秒。
  写请求超时不自动重放，提示先刷新核对。结果筛选存在竞态时不让旧响应覆盖新条件。
- 导出改为锁定“已成功应用”的筛选条件，失败或未应用时不导出；导出返回非预期文件时不保存。
  Trends API CSV 在既有七列结构下输出话题行和相关报道行。
- 隔离 PostgreSQL/Redis 回归：463 项通过、6 项跳过、0 失败。浏览器注入 20 秒延迟后 20.02 秒进入失败态、
  busy 清除并保留旧数据；重试恢复；筛选竞态未串数据；分页 26–50 正常；无 JS 错误。
- 生产轻量汇总冷计算实测：all 5.175 秒、Web 1.509 秒、News 2.290 秒、Trends 0.042 秒；
  数值为 39,830 请求 / 29,601 查询词 / 522,676 去重链接。这是当次测量，不作为 SLA。
- 线上浏览器验收：首页汇总与最近结果正常；任务 15 行、结果页 25 行、下一页 26–50 正常；
  未登录访问汇总返回 401；390px 无横向溢出。已有 Trends API 任务导出为 38 行（10 话题 + 28 报道），
  CSV 链接与 JSONL 逐项一致。
- 发布前后不变：原始请求 39,835、历史 pages 332,768、持续采集 false、正文 false、Whale 上传/领取 false、
  启用监测 0、公开投影 39,830。未创建新搜索任务，未运行旧迁移。

已知边界：7 列 API CSV 仍是 JSONL 原始结构的扁平子集，不包含全部字段；CSV 行数不等于链接数。
本站当前分析接口在部分浏览状态下曾显示一次“服务暂不可用，请稍后重试”，随后报告内容正常；
该完整分析链路未在本轮重构，不能宣称其冷查询 SLA 已解决。
