# Google 采集增强方案进度（2026-09-10）

目标：借鉴帖子经验增强 Google 搜索层稳定性，不改变现有主链路

借鉴方法，不复制帖子项目；不使用指纹伪造、CAPTCHA 绕过或未授权代理。

## 已完成（代码，待测试验证）

- 每页请求分类证据：`results / empty / parse_failure / javascript_verification / captcha / timeout / http_error`，
  记录通道、页码、代理哈希、HTTP 状态、结果数、耗时、原始 HTML 的 SHA-256。
- 空页判断修正：空结果最多用一个备用通道核验后才缓存；解析失败绝不缓存为"无结果"；
  第 7 页为空不会跳过后续页（空页正常返回，页循环不中断）。
- 持久化 Chrome 通道 `persistent_browser`：默认关闭；每个代理哈希独立浏览器配置目录，
  30 秒请求间隔，达到请求数 / 运行时间 / 失败阈值后重建；有 `DISPLAY` 有头，否则标记 headless；
  崩溃只重建当前代理的上下文；配置目录权限 0700，与日常 Chrome 隔离。
- 代理质量指标：CAPTCHA 数、JS 验证数、HTTP 错误数、超时数、连续失败、累计延迟；
  长期低成功率（≥20 样本且成功率 <20%）代理自动隔离 1 小时。
- `google_serp_attempts` 表：持久化每页证据；统计接口新增各通道成功率、P50/P95、
  各代理成功率与 P95、隔离计数。
- 测试模式完整 HTML 证据：`GOOGLE_SERP_SAVE_HTML=true` 时按 SHA-256 存到
  `state/serp-evidence/`，文件权限 0600，不含代理凭据。

## 关键设计决策（怎么理解）

- 证据先行：先把"请求成功但无法判断页面内容"变成可分类、可追溯的记录，
  再谈通道替换。没有基线数据就不宣称成功率。
- 持久化浏览器只是可选实验通道：`PERSISTENT_BROWSER_ENABLED=false` 时路径与现状完全一致；
  启用后顺序为 `persistent_browser → wml → wml_direct → searxng`，随时可关。
- 上下文按代理哈希共享并加锁：同一代理跨线程复用同一浏览器，间隔在锁内保证；
  不同代理永不共享配置目录，避免会话串号和 Chrome Profile 锁冲突。
- 隔离不等于封禁：低成功率代理只是暂停调度，窗口过去后自动恢复观察；
  新代理没有历史样本，始终允许试用。
- 90% 成功率只作观察目标，不作为承诺；任何结论都要有原始证据（SHA-256 / HTML 文件）支撑。
